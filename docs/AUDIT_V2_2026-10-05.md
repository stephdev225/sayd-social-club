## 2. Ce qui est bon (à conserver)

- **Le choix Next.js App Router.** Il fournit déjà le backend dont on a besoin : les Route Handlers (`app/api/*`) exécutent du code serveur, donc la clé Stripe et Firebase Admin restent côté serveur. Pas besoin d'un serveur Express séparé.
- **L'i18n FR/EN** par segment `[lang]` avec dictionnaires JSON : simple, fonctionne, FR par défaut.
- **L'identité sombre** : noir mat `#050505`, or `#D5B038`, Cormorant Garamond (titres) + DM Sans (texte). La hiérarchie typographique du hero est forte.
- **`ScrollReveal`** : léger (IntersectionObserver + CSS), respecte `prefers-reduced-motion`, a un repli de sécurité. Bon composant.
- **Pas de débordement horizontal** sur mobile (vérifié à 390 px) et menu mobile plein écran correct.
- **Spotify embed** (Sayd Social Radio) : bonne idée de marque.
- Données structurées JSON-LD `Organization` dans le layout.

## 5. Audit design

**Fort** : le hero (grand titre serif, « Club » italique or), le contraste noir/or, les espacements généreux, le rythme des sections.

**Faible ou générique** (selon ta propre direction créative) :
- Pastille « The New Era of Nightlife » avec point qui clignote, halo flou, texture de bruit, glassmorphism, `rounded-[2rem]` partout, ombres dorées : exactement la liste « à éviter » de `CREATIVE_DIRECTION_MASTER.md`.
- Les photos stock donnent l'impression d'une soirée quelconque, pas de **cette** communauté afro-caribéenne de Québec. C'est le principal problème de crédibilité.
- La palette du brief (terracotta profond, sable doré, vert bouteille, noir charbon) est réduite à noir + or. On perd la chaleur « Miami / Lagos / Toronto » demandée.
- Le logo est un PNG 612×408 inversé en CSS ; il paraît fin et petit dans la barre de navigation. Un SVG fourni par le graphiste serait net à toutes les tailles.
- Images à `opacity-40/50/60` en permanence : les photos sont éteintes, l'énergie de la soirée disparaît.

**Direction proposée** (à valider, puis à écrire dans `ART_DIRECTION.md`) : garder noir + or comme base, réintroduire **terracotta** pour les états d'action et le **vert bouteille** en surfaces secondaires ; vraies photos plein cadre et pleine opacité, recadrées serré sur les gens ; moins de cartes arrondies, plus de compositions éditoriales (grandes images, texte aligné sur une grille) ; animation limitée au reveal existant.

## 7. Architecture recommandée

```
                       Navigateur (public / admin / scanner)
                                     │
                    Next.js sur Vercel (une seule application)
         ┌───────────────────────────┼─────────────────────────────┐
   Pages publiques           Route Handlers (serveur)          /admin + /scan
   (événements, billets)     /api/checkout                     (Firebase Auth,
                             /api/stripe/webhook                 rôle admin/staff)
                             /api/admin/*  /api/scan
                                     │
                 ┌───────────────────┴───────────────────┐
           Stripe (TON compte)                    Firestore (Admin SDK,
           Checkout + webhooks                     serveur uniquement)
                 │                                         │
                 └──── checkout.session.completed ─────────┘
                                     │
                     commande payée → billets + QR → courriel
```

| Couche | Choix | Raison |
|---|---|---|
| Front + back | **Next.js (déjà en place), mis à jour** vers la dernière version corrigée | Pas de réécriture ; les Route Handlers servent de backend |
| Hébergement | **Vercel** | Natif Next.js, fonctions serveur pour le webhook, déploiements de prévisualisation pour tester avant la prod |
| Base | **Cloud Firestore** | Ton choix ; transactions atomiques pour le stock et le check-in |
| Accès aux données | **Admin SDK côté serveur uniquement.** Règles Firestore : **tout refusé côté client** | Le navigateur ne lit ni n'écrit jamais Firestore directement. Surface d'attaque minimale. |
| Auth admin | **Firebase Authentication** (courriel + mot de passe) + **custom claims** `admin` / `staff` + cookie de session `httpOnly` vérifié côté serveur | `/admin` et `/scan` protégés côté serveur, pas seulement masqués |
| Paiement | **Stripe Checkout**, compte Sayd, **sans Connect** | L'argent arrive directement sur ton compte |
| Courriels | **Brevo** (déjà prévu dans le code) ou Resend | Envoyés depuis le webhook, jamais depuis la page de succès |
| QR | Librairie `qrcode` côté serveur | Génération PNG/SVG pour courriel et page billet |
| Analytics | **Vercel Web Analytics** (sans cookies) + événements d'entonnoir | Aucune donnée personnelle ; séparé des données clients |
| Validation | **Zod** sur toutes les entrées API | Fin des données non validées |

## 8. Modèle de données (Firestore)

Adapté de ta proposition. Changements : prix en **cents** (entiers, jamais de flottants), commande avec **lignes** pour pouvoir acheter VIP + Général en une fois plus tard, un compteur `reserved` pour le stock, et une collection d'idempotence Stripe.

```
events/{eventId}
  slug, name{fr,en}, description{fr,en}, startsAt, endsAt, venueName, address,
  capacity, status: draft|published|sold_out|cancelled|archived,
  coverImage, dressCode?, lineup?[], createdAt, updatedAt

ticketTypes/{ticketTypeId}
  eventId, name{fr,en}, description{fr,en}, priceCents, currency: "cad",
  quantityTotal, quantitySold, quantityReserved,   // disponible = total - sold - reserved
  maxPerOrder, salesStartAt?, salesEndAt?, active, sortOrder

customers/{customerId}
  firstName, lastName, email (normalisé), phone?, marketingOptIn, createdAt

orders/{orderId}                    // ex. "ORD-7K3M9QX2"
  eventId, customerId, items[{ticketTypeId, name, quantity, unitPriceCents}],
  amountCents, currency, status: pending|paid|expired|failed|refunded|cancelled,
  channel: online|door,
  stripeCheckoutSessionId, stripePaymentIntentId?,
  expiresAt, createdAt, updatedAt, paidAt?

payments/{paymentId}
  orderId, stripeCheckoutSessionId, stripePaymentIntentId, amountCents,
  currency, status: paid|pending|failed|refunded, paidAt?, refundedAt?

tickets/{ticketId}                  // ex. "SAYD-26-8QK4M2TZ7P" — aussi le contenu du QR
  orderId, eventId, customerId, ticketTypeId, holderName,
  status: valid|used|cancelled|refunded,
  checkedInAt?, checkedInBy?, createdAt

stripeEvents/{stripeEventId}        // idempotence : un document par événement Stripe traité
  type, processedAt, orderId

checkins/{autoId}                   // journal de chaque scan, y compris refus
  ticketId, eventId, result: ok|already_used|invalid|wrong_event|cancelled,
  scannedBy, scannedAt
```

Rôles : stockés en **custom claims** Firebase (`admin`, `staff`), posés par un script serveur. Pas de collection `admins` lisible par le client.

## 9. Flux Stripe

```
1. Client choisit billet + quantité, entre prénom, nom, courriel (téléphone optionnel)
2. POST /api/checkout  (validation Zod + limite de requêtes)
3. Transaction Firestore :
     disponible = total - sold - reserved ; si quantité > disponible → refus "complet"
     reserved += quantité ; création customer + order "pending" (expiresAt = +30 min)
4. Création Stripe Checkout Session :
     prix lus EN BASE (jamais du navigateur), expires_at = +30 min,
     metadata { orderId }, client_reference_id = orderId, customer_email
5. Redirection vers Stripe → paiement
6. Webhook POST /api/stripe/webhook
     a. signature vérifiée avec STRIPE_WEBHOOK_SECRET sur le corps brut
     b. checkout.session.completed + payment_status = "paid" :
        TRANSACTION { si stripeEvents/{event.id} existe → stop (doublon)
                      si order.status = "paid" → stop
                      order → paid ; payment créé ; N tickets créés ;
                      reserved -= q ; sold += q ; stripeEvents/{event.id} créé }
        puis envoi du courriel (marqué envoyé sur la commande pour ne pas renvoyer)
     c. checkout.session.async_payment_succeeded / _failed : même logique
     d. checkout.session.expired : order → expired ; reserved -= q (libère le stock)
     e. charge.refunded : order → refunded ; billets → refunded (le QR devient invalide)
7. Page /billetterie/succes?session_id=… : AFFICHE l'état lu en base
   ("paiement en cours de confirmation…" tant que le webhook n'est pas passé). Elle ne valide rien.
```

**Pourquoi ce stock tient** : la réservation est faite dans une transaction Firestore au moment où le client part payer. Deux personnes ne peuvent pas réserver le dernier billet : la deuxième transaction relit le compteur et échoue. Si le client abandonne, Stripe envoie `checkout.session.expired` après 30 min et la place revient en vente. Le webhook ne fait que convertir `reserved` en `sold`.

## 10. Check-in et vente à la porte (ton vrai besoin)

Tu veux arrêter lepointdevente **et** les factures Stripe manuelles à la porte. Les deux passent par le même système :

**Scanner `/scan`** (téléphone du staff, connecté avec un compte `staff`) :
- caméra → lecture du QR → `POST /api/scan` → transaction : `valid` → `used` (+ heure, + qui) ; sinon réponse claire : **DÉJÀ UTILISÉ à 22 h 14**, **INVALIDE**, **AUTRE ÉVÉNEMENT**, **REMBOURSÉ**.
- grand écran vert/rouge, son, nom du détenteur et type de billet.
- **Authenticité** : l'identifiant du billet est aléatoire (≈ 50 bits, impossible à deviner) et n'existe que dans ta base. Une capture d'écran copiée ne passe qu'**une seule fois** : le deuxième scan affiche « déjà utilisé ».
- Saisie manuelle du code si le QR est abîmé ; recherche par nom/courriel.

**Vente à la porte** (`/admin/porte`) :
- le staff choisit le billet et la quantité → le système crée une commande `channel: door` et affiche **un QR Stripe Checkout** sur son écran → le client paie avec son propre téléphone (Apple Pay / carte) → même webhook → billet créé et marqué **directement utilisé**.
- option « payé comptant » (enregistré par un admin, sans Stripe) pour garder les chiffres complets.
- Plus tard, si tu veux taper la carte sur ton téléphone : Stripe Terminal / Tap to Pay. Pas nécessaire pour la V1.

## 11. Dashboard admin `/admin`

Barre latérale : **Vue d'ensemble · Événements · Billets · Commandes · Participants · Paiements · Check-in · Porte**.

- **Vue d'ensemble** (filtrable par événement) : revenus (payé − remboursé), billets vendus / disponibles / capacité, commandes, taux de check-in le soir même, entonnoir *visites → clics billetterie → checkout commencé → payé* (taux de conversion calculé seulement à partir des événements anonymes).
- **Commandes** : n°, client, courriel, événement, billets, montant, statut, date, lien vers la session Stripe ; recherche, filtres statut/événement, tri par date ; export CSV.
- **Participants** : liste par événement, statut de chaque billet (valide / utilisé), export CSV pour la liste de porte de secours.
- **Événements / Billets** : créer, modifier, publier, désactiver ; types de billets avec prix, stock, vendus, disponibles.
- **Paiements** : payé / en attente / échoué / remboursé. Le **dashboard Stripe reste la source officielle** pour les montants et les virements.
- États chargement, vide, erreur ; utilisable sur tablette ; même identité que le site mais plus sobre.

## 12. Sécurité (ce que je mettrai en place)

- Clé secrète Stripe, secret webhook, compte de service Firebase : **variables serveur uniquement**, jamais `NEXT_PUBLIC_`. `.env.local` ignoré par git ; `.env.example` sans valeurs.
- Règles Firestore : `allow read, write: if false;` partout (tout passe par le serveur).
- `/admin/*`, `/scan`, `/api/admin/*`, `/api/scan` : vérification du cookie de session **et** du claim côté serveur à chaque requête.
- Webhook : signature vérifiée, corps brut, idempotence par `event.id`.
- Prix et stock lus en base, jamais envoyés par le navigateur.
- Validation Zod, limite de requêtes sur `/api/checkout`, `/api/scan` et les formulaires, échappement HTML de tous les courriels.
- En-têtes de sécurité (CSP, HSTS, `X-Frame-Options`).
- Politique de confidentialité (Loi 25) : quelles données, pourquoi, combien de temps, qui contacter. Visiteurs anonymes : analytics sans cookies, aucune donnée personnelle.
